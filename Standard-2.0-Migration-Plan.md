## 1. Overview / scope

This session covers **`Booker.Saule` only** (this repo, `C:\WORKSPACE\Booker\saule`). A second, related project — **`Saule.Extended`**, living in a *different* repo at `C:\WORKSPACE\Booker\Booker.Core.Infrastructure.Libraries\Saule.Extended\` — depends on this package but its **migration** is explicitly out of scope for this session. Per a later instruction in this same session, `Saule.Extended`'s *source was read* (read-only, no edits) specifically to verify exactly which `Saule` APIs it consumes, so that this plan's consumer-impact analysis is real rather than inferred — see [Section 3.4](#34-consumer-function-level-verification-crm-bookermain-sauleextended).

Saule is a fork of the open-source [joukevandermaas/saule](https://github.com/joukevandermaas/saule) JSON:API (jsonapi.org) serialization library for ASP.NET Web API 2. The real, internally-consumed lineage is the `booker-saule` branch — a long-lived fork carrying Booker-specific features on top of upstream (see Section 3.0) — published to an internal feed as NuGet package **`Booker.Saule`**. It provides a `MediaTypeFormatter`, attributes, and a `JsonApiSerializer<T>` that let an ASP.NET Web API 2 controller return/accept JSON:API-formatted payloads, plus a portable query/serialization core (filtering, sorting, pagination, fieldsets, resource-graph traversal, and a pluggable `IApiResourceProvider` resolution layer) built only on Newtonsoft.Json and reflection.

## 3. Analysis

### 3.0 Branch correction — why this matters

The first pass of this analysis was done against `booker/pbi/1538115_analysis_standard2` as it existed at the time, which turned out to be **byte-identical to `origin/master`** (the upstream OSS `joukevandermaas/saule` tree) — commit `5fea3d6`. Cross-checking actual consumed API surface against the real, restored `Booker.Saule.1.7.0.22.dll` in `BookerMain`'s NuGet cache revealed a **`Saule.Resources`** namespace (`IApiResourceProvider`, `IApiResourceProviderFactory`, `DefaultApiResourceProvider`, `DefaultApiResourceProviderFactory`) that does not exist anywhere on `master` — it was added on **`origin/booker-saule`** (32 commits ahead of `master`, commits `c508f7b`/`78c3401`/`de8c64b`, "Added IApiResourceProvider and IApiResourceProviderFactory") and never merged upstream. `BookerMain`'s `V5ApiResourceProvider.cs` directly subclasses this type — meaning any migration done against `master` would have shipped a `Booker.Saule` build **missing a type a real consumer depends on today**, independent of anything TFM-related.

The user re-created `booker/pbi/1538115_analysis_standard2` from `origin/booker-saule`. **Verified this session:** `git rev-list --left-right --count HEAD...origin/booker-saule` → `0 0`, and `git merge-base --is-ancestor HEAD origin/booker-saule` succeeds — the branch is now exactly `origin/booker-saule` at commit `de8c64b`. All analysis below is against this corrected tree. (One side effect of the correction: the earlier-flagged "`Booker.Saule` vs. `saule` package-id discrepancy" is **resolved** — `Saule.nuspec` on this branch already says `<id>Booker.Saule</id>` ([Saule.nuspec:4](Saule/Saule.nuspec#L4)); that discrepancy was itself an artifact of being on the wrong branch.)

**Two corrections found during Phase 1 implementation (2026-09-09), not caught by the file-level `using`-statement scan above — surfacing them here rather than silently fixing them, same as the prior migrations' "new finding" callouts:**

1. **`JsonApiSerializer.cs`** (read in full before starting Phase 1b) is **~90% portable, not hard-blocked** — its `using System.Web.Http;` and both `HttpError` branches are confined to one small private method, `GetAsError(object)` ([JsonApiSerializer.cs:111-132](Saule/JsonApiSerializer.cs#L111-L132) as it existed pre-migration). Everything else (`PreprocessContent`, the public `Serialize(PreprocessResult)`, `GetJsonSerializer`, all properties, the `Exception`-branch of `GetAsError`) has zero framework dependency. This matters because **the portable `JsonApiSerializerOfT.cs` directly calls `new JsonApiSerializer()` and `JsonApiSerializer.Serialize(...)`** ([JsonApiSerializerOfT.cs:38,101](Saule/JsonApiSerializerOfT.cs#L38)) — so `JsonApiSerializer.cs` **must** ship on all 3 TFMs, not just `net47`, or the portable core wouldn't compile at all on `netstandard2.0`/`net10.0`. **Resolution:** kept `JsonApiSerializer.cs` in the portable set, with `GetAsError`'s two `HttpError`-specific branches wrapped in `#if NETFRAMEWORK` / `#elif NET10_0` (checking `Microsoft.AspNetCore.Mvc.ProblemDetails` instead) / `#else` (no-op, `Exception`-only) — same `#if`-guard pattern the `Booker.ApplicationInsights` migration used for its own framework-only method bodies.
2. **`Serialization/ApiError.cs`** has the identical shape — the `Exception`-based constructor, `Title`/`Detail`/`Code`/`Links` properties, and `IsClientError` are portable; only the `internal ApiError(HttpError ex)` constructor and its `GetRecursiveExceptionMessage(HttpError ex)` helper need `System.Web.Http`. Same `#if NETFRAMEWORK`/`#elif NET10_0`/`#else` resolution — added a `net10.0`-only constructor overload taking `Microsoft.AspNetCore.Mvc.ProblemDetails` instead of `HttpError`.
3. **`Http/JsonApiProcessor.cs`** moves from "soft/portable" to **the net47-only bucket** (making it 15 files there, not 14) — it compiles fine against `System.Net.Http.Formatting`'s netstandard2.0 asset (technically "soft"), but its `ObjectContent`/`response.Content` usage and its only two callers (`JsonApiAttribute.cs`, `PreprocessingDelegatingHandler.cs`) are both exclusively part of the classic Web API 2 message-handler pipeline — verified via `grep -rn "JsonApiProcessor\."`, zero portable-core callers found. Shipping it on `netstandard2.0` would just be unreferenced dead code with no consumer. Its logic (`Accept`-header/status-code short-circuit checks) is folded directly into the new `net10.0` `JsonApiOutputFormatter`/`JsonApiResultFilter` (Section 7.1) rather than given a literal same-named twin, since ASP.NET Core's automatic content negotiation removes most of the reason it existed as a separate class.

**Revised net effect:** portable core is **65 files** (62 + `JsonApiSerializer.cs` + `Serialization/ApiError.cs`, both now `#if`-guarded, minus nothing — the 2 "soft" files stay soft), **3 soft** (`JsonApiSerializerOfT.cs` + the 2 `Resources/*Factory.cs`), **15 net47-only with a planned `net10.0` equivalent** (the original 14 + `JsonApiProcessor.cs`, whose net10.0 equivalent is absorbed into other new files rather than 1:1 twinned).

This is **pre-existing today, unrelated to this migration**, but it means this feature must never be dropped in any future rebase/upstream-sync of this repo, and is exactly the kind of thing that would have silently broken `BookerMain` had the original (uncorrected) branch's analysis been acted on.

## 4. Decision

**DECIDED (2026-09-09, user + assistant discussion): Approach B — multi-target `netstandard2.0;net47;net10.0` now, including a real ASP.NET Core (net10.0) reimplementation of the 14 System.Web.Http-only files, built today rather than deferred.** Rationale: the org's stated end goal is migrating consumer apps (starting with BookerMain/CRM) to .NET 10, and it's cheaper/lower-risk to build and validate the ASP.NET Core wiring against Saule's own test suite now than to reverse-engineer it later under consumer migration time pressure. ## 7. Deep-dive: challenges & risks — decisions made before implementation (all resolved, kept for the record)

These were the open questions this plan couldn't resolve unilaterally when first raised — all resolved by the time implementation happened (see the resolution note right after the list, and Sections 4/10.1 for what was actually decided/built):

1. **`net47` vs. `net471` bump.** Sibling repos (`Booker.ApplicationInsights`, `Booker.Core.Infrastructure.Libraries.WebApi`) both multi-target from a `net471` baseline; this repo currently sits on `net47`. Bumping is not required by anything found in Saule's own dependency set — `Microsoft.AspNet.WebApi.Core`/`.Client` 5.2.7 and `Newtonsoft.Json` 12.0.1 all support `net47` fine. **Trade-off:** staying on `net47` is a smaller, purely-additive diff (only adds `netstandard2.0`); bumping to `net471` adds consistency with the two prior migrations but touches the framework baseline for a project with 4 live consumers, for no functional gain. **My recommendation: stay on `net47`, no bump** — but this is your call.
2. **Is the `netstandard2.0` asset actually wanted right now?** Confirmed in Section 3.4: **no current consumer benefits from it** — all 4 host on classic ASP.NET Web API 2. This migration is pure multi-target-readiness for the org-wide initiative. **Decision needed:** is that still the goal, or should this session's effort be redirected (e.g., toward `Saule.Extended` instead, or toward something with nearer-term payoff)? I'd lean toward proceeding — it's cheap (Section 8 estimate) and de-risks whenever a consumer does eventually move — but wanted to surface it explicitly rather than assume.
3. **Portable-core scope: exactly 66 files, or should `Resources/*Factory.cs` also move net47-only for symmetry?** `IApiResourceProviderFactory.Create(HttpRequestMessage request)` only needs `System.Net.Http`, which *is* netstandard2.0-compatible — so it's technically includable in the portable set.           if (request.Properties.TryGetValue(Saule.Extended.Consts.JsonApiResourceDescriptor, out object resource))
  ```csharp
          {
              var apiResource = resource as ApiResource;
              if (apiResource != null)
                  return new V5ApiResourceProvider(apiResource);
          }

          return new V5ApiResourceProvider(null);
      }
  }
  ```
  This compiles and behaves identically on `net10.0` for two independently-verified reasons: **(1)** `IApiResourceProviderFactory`/`ApiResource` are portable (Section 3.2), and **(2)** the string key it reads, `Saule.Extended.Consts.JsonApiResourceDescriptor` = `"Saule_ResourceDescriptor"` (confirmed by reading `Saule.Extended/Consts.cs:9` directly), is the exact same string `Saule`'s own portable `Resources/ResourceDescriptor.cs` writes via `Constants.PropertyNames.ResourceDescriptor` — so whatever populates `request.Properties` (net47's `ReturnsResourceAttribute`, or net10.0's, via the `HttpContext`→`HttpRequestMessage` shim in `Http/NetCore/HttpContextRequestMessageExtensions.cs`) is read back correctly regardless of which TFM produced it.
- **New requirement, not present today: something must construct an `HttpRequestMessage` from the real `HttpContext.Request` at the point `IApiResourceProviderFactory.Create(...)` is invoked**, since ASP.NET Core's native request type is `HttpContext`/`HttpRequest`, not `HttpRequestMessage`. - **`SauleUrlPathBuilder`** ([Infrastructure/SauleUrlPathBuilder.cs](../BookerMain/src/SpaFinder.SpaBooker/API/SpaFinder.SpaBooker.WebApi/Infrastructure/SauleUrlPathBuilder.cs)) — subclasses the portable `DefaultUrlPathBuilder`. **No change needed.**
- **`[Paginated(...)]` usage** — CRM's real code ([Controllers/CustomersController.cs:44](../CRM/src/Booker.CRM.Api/Controllers/CustomersController.cs#L44)):
  ```csharp

  public IHttpActionResult GetCustomers(...)
  ```
  **No consumer-code change needed** — this line is byte-identical on `net10.0`, since `Saule.Http.PaginatedAttribute` exists under the exact same fully-qualified name there (verified via a direct binary scan of both built assemblies, Section 9). ### 11.1 Reference code for `Saule.Extended`'s own `net10.0` rewrite

The real current code, and the shape of the change needed, using the same pattern `Saule`'s own `Http/NetCore/*.cs` files already establish. **This section is a starting-point sketch for the next session, not implemented or built** — `Saule.Extended` is out of scope for this session, per Section 1.

**Real current code** ([Resources/AllowOperationsAttribute.cs](../Booker.Core.Infrastructure.Libraries/Saule.Extended/Resources/AllowOperationsAttribute.cs), abridged to the parts that touch Saule's net47-only types):
```csharp
using System.Web.Http.Controllers;
using System.Web.Http.Filters;

public class AllowOperationsAttribute : ActionFilterAttribute
{
    private AllowsQueryAttribute _allowsQueryAttribute = new AllowsQueryAttribute();

    public override void OnActionExecuting(HttpActionContext actionContext)
    {
        var validateQueryParamsAttrs = actionContext.ActionDescriptor.GetCustomAttributes<ValidateQueryParamsAttribute>();
        // ... AllowedOperations.Include / .Fields branch ...
        _allowsQueryAttribute.OnActionExecuting(actionContext);

        // ... AllowedOperations.Filter branch ...
        var queryParams = actionContext.Request.GetQueryNameValuePairs().ToList();
        var returnsResourceAttributes = actionContext.ActionDescriptor.GetCustomAttributes<ReturnsResourceAttribute>();
        var queryContext = actionContext.Request.Properties["Saule_QueryContext"] as QueryContext;

        // ... AllowedOperations.PageSort / .Sort branch ...
        var paginatedAttribute = new PaginatedAttribute { FirstPageNumber = 1 };
        paginatedAttribute.OnActionExecuting(actionContext);
        new HandlesQueryAttribute().OnActionExecuting(actionContext);
```

**`net10.0` rewrite sketch** — every substitution below is the exact one `Saule`'s own `Http/NetCore/HandlesQueryAttribute.cs`/`PaginatedAttribute.cs`/`AllowsQueryAttribute.cs` already made, so `Saule.Extended` doesn't need to invent a new pattern, just apply the same one:
```csharp
using Microsoft.AspNetCore.Mvc.Filters;   // was: System.Web.Http.Filters

public class AllowOperationsAttribute : ActionFilterAttribute
{
    private Saule.Http.AllowsQueryAttribute _allowsQueryAttribute = new Saule.Http.AllowsQueryAttribute();

    public override void OnActionExecuting(ActionExecutingContext context)   // was: HttpActionContext actionContext
    {
        // GetCustomAttributes<T>() -> FilterDescriptors (action-level) - ASP.NET Core doesn't
        // separate "action" vs "controller" descriptors the same way; context.Filters covers both.
        var hasValidateQueryParams = context.Filters.OfType<ValidateQueryParamsAttribute>().Any();

        _allowsQueryAttribute.OnActionExecuting(context);   // same call, now takes ActionExecutingContext

        // GetQueryNameValuePairs() -> the same IQueryCollection.ToNameValuePairs() extension
        // Saule.Http.IQueryCollectionExtensions already defines (internal to Saule - Saule.Extended
        // would need its own copy, or Saule could make it public if this pattern recurs elsewhere).
        var queryParams = context.HttpContext.Request.Query.ToNameValuePairs().ToList();
        var returnsResourceAttributes = context.Filters.OfType<Saule.Http.ReturnsResourceAttribute>().ToList();

        // request.Properties[...] -> HttpContext.Items[...] (same string key, Section 11's
        // V5ApiResourceProviderFactory note applies identically here).
        var queryContext = context.HttpContext.Items["Saule_QueryContext"] as QueryContext;

        var paginatedAttribute = new Saule.Http.PaginatedAttribute { FirstPageNumber = 1 };
        paginatedAttribute.OnActionExecuting(context);
        new Saule.Http.HandlesQueryAttribute().OnActionExecuting(context);
    }
}
```
**What carries over with zero translation:** every Saule type referenced (`AllowsQueryAttribute`, `ReturnsResourceAttribute`, `PaginatedAttribute`, `HandlesQueryAttribute`, `QueryContext`) — same fully-qualified names on `net10.0`, verified this session (Section 4's correction note). **What genuinely needs rework, specific to `Saule.Extended`'s own code:** the base class, the method signature, `GetCustomAttributes<T>()` → `context.Filters.OfType<T>()`, `GetQueryNameValuePairs()` → an `IQueryCollection`-based equivalent, and `request.Properties[...]` → `context.HttpContext.Items[...]`. The same 5 substitutions apply near-identically to `ValidateQueryParamsAttribute.cs` and `DynamicReturnsResourceAttribute.cs` (not sketched here — same pattern, larger files, not audited line-by-line this session).
